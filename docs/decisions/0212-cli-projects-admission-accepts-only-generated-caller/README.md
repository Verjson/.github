# 0212 — CLI Projects admission accepts only the generated CI caller

- **Date:** 2026-09-29
- **Status:** Accepted for implementation; ruleset activation remains human-gated
- **Issue:** [Verjson/.github#1646](https://github.com/Verjson/.github/issues/1646)
- **Related decision:** [ADR 0153](../0153-cli-projects-package-surface-required-workflow/README.md)
- **Category:** protected workflow admission (sensitive class)

## Context

The unmerged implementation work for issue #1646 proposed a temporary legacy caller exception while the CLI Projects default branch moved to the generated workflow. Review found that a successful required-workflow run is attached to its PR head. A strict required status check refreshes an ordinary PR head when it falls behind `main`, but it cannot invalidate a successful result when that head already contains the commit that later advances `main`. Such a PR could restore the old caller and keep its success.

## Decision

The protected pull request workflow accepts only the byte-exact caller generated by its immutable required-workflow revision. It never embeds or accepts the previous-main digest. The `rollout_legacy_consumer_workflow_sha256` value is limited to the ruleset rotation verifier, which may use it to confirm the existing default-branch caller while the generated caller change is prepared; it is not an admission exception for PR heads.

Keep the strict `admission` status check and bind rollout verification to a successful check for the exact head from the same required-workflow run. Strict freshness is defense in depth; the safety property comes from replacing the active required-workflow revision with one that rejects every non-generated caller. Remove the rollout-only digest after [Verjson/verjson-cli-projects#142](https://github.com/Verjson/verjson-cli-projects/pull/142) lands and the default branch matches the generator.

The ruleset rotation remains behind the explicit acknowledgment in the rollout contract. This ADR authorizes the implementation and does not authorize applying the live organization ruleset without that acknowledgment.

## Consequences

PRs with the previous caller fail admission after the new workflow revision is activated and must update their caller. Existing successful checks from the old workflow revision do not satisfy the newly pinned required-workflow rule.
