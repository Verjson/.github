# Canonical CI adopter bootstrap

Use `scripts/bootstrap-canonical-ci.py` to check or converge the organization-facing
contract without adopting Verjson-branded configuration names.

## Owner prerequisites

1. Fork or clone the canonical contract at one reviewed 40-character commit SHA.
2. Register each required GitHub App in the adopting owner account, disable webhooks,
   select the repositories declared in the manifest, and install it. GitHub App
   registration and private-key generation are owner-mediated GitHub UI operations;
   the ordinary REST API cannot replay them idempotently.
3. Enter each App's exact slug, App ID, client ID, installation ID, permissions,
   events, and repository selection in the manifest. The bootstrap validates these
   fields and never modifies or widens an App.
4. Export each secret value under the environment-variable name declared by the
   manifest. Values are consumed only by `apply`, through standard input to `gh`, and
   never appear in the receipt.
5. Authenticate `gh` as an active owner of the target organization. The token needs
   organization Actions-variable/secret administration and read access to the App
   installation inventory.

Start from `docs/examples/canonical-ci-bootstrap.json`. Replace all sample identities;
do not reuse another organization's App IDs, installation IDs, client IDs, or keys.
The permission maps in that example are the maximum canonical role contracts. Remove
an unused role rather than broadening it.

## Run

```sh
python3 scripts/bootstrap-canonical-ci.py dry-run adopter.json \
  --workspace /path/to/adopter-worktrees \
  --contract-root /path/to/Verjson-.github \
  --receipt bootstrap-dry-run.json

python3 scripts/bootstrap-canonical-ci.py apply adopter.json \
  --workspace /path/to/adopter-worktrees \
  --contract-root /path/to/Verjson-.github \
  --receipt bootstrap-apply.json

python3 scripts/bootstrap-canonical-ci.py check adopter.json \
  --workspace /path/to/adopter-worktrees \
  --contract-root /path/to/Verjson-.github
```

`dry-run` reads live metadata and generates outputs in memory but writes nothing and
does not require secret values. `apply` updates drifted variables, uploads every
declared opaque secret, and atomically replaces declared generated outputs only after
all generation succeeds. `check` requires readable settings and generated bytes to
match. Because GitHub does not return secret values, `check` proves only the secret's
name and visibility; apply is the idempotent value-convergence operation.

Each caller entry names a repository directory beneath `--workspace`, an allowlisted
generator, its arguments excluding the contract SHA, and its output. For changelog
generation, the first argument is the generator mode. Every caller receives the one
top-level immutable `contract_sha`; mutable branches and mixed pins are rejected.

## App roles and trust boundaries

- Review authorization: Checks write, Contents read, Pull requests write, Metadata
  read. It authors head-bound review authorization; it does not merge.
- Terminal merge: Contents write, Pull requests write, Metadata read. Ruleset bypass
  is a separate owner action and is not inferred or configured by this script.
- Release: Contents write and Metadata read. Its ruleset bypass is likewise separate.
- Renovate compatibility: Actions, Checks, Contents, Pull requests, and Commit
  statuses read, plus Metadata read. It has no write permission.
- Dependency supersession: Contents read, Pull requests write, and Metadata read. Its
  private key is delivered only to the exact-repository terminal reconciliation token
  mint; observation continues to use the read-only Renovate compatibility role.

Dependency supersession adopters provide organization variable
`DEPENDENCY_SUPERSESSION_APP_CLIENT_ID` and secret
`DEPENDENCY_SUPERSESSION_APP_PRIVATE_KEY`. Do not create
`DEPENDENCY_SUPERSESSION_WRITE_ENABLED` during initial bootstrap: its absence keeps the
terminal reconciler observe-only until a reviewed disposable canary explicitly enables
the rollout gate.

All canonical role Apps subscribe to no webhook events and this bootstrap supports
only all-repository installations, whose scope is completely observable in the
organization installation inventory. If an installation reports a different event,
permission, identity, suspension, or repository selection, bootstrap stops. A future
selected-repository mode requires a new manifest allowlist and paginated exact
repository-membership validation; it must not reuse this mode's evidence.

## Rollback and legacy coexistence

Reapply the prior reviewed manifest and immutable contract SHA. Keep legacy
organization-branded variables while immutable historical callers still reference
them; the bootstrap neither creates nor deletes those names. Secret rollback requires supplying
the previous secret value. App key revocation/rotation and ruleset bypass removal are
manual owner actions and should be recorded with the run receipt.
